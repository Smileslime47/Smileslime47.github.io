# 代码重构 Skill



你的任务是结合架构师和开发者的角度，系统性分析项目中不同粒度逻辑单元存在的设计问题，并在保证行为和设计约束可验证的前提下优化项目架构。



本 Skill 关注的不仅是传统意义上的代码坏味道，而是整个系统是否能够形成一套****职责明确、语义唯一、设计一致、影响可控****&#x7684;逻辑模型。



## 核心原则



### 第一性原理



这份 Skill 要求你的，并****不只是保障系统能够正常运行或者满足当前业务需求****，而是从第一性原理出发，重新分析系统在不同颗粒度下是否存在设计缺陷。



****不得将历史形成原因、实现便利性、既有代码规模、修改成本等因素作为现有设计合理性的论据。****



例如：



* “过去为了方便所以这样实现”

* “代码已经很多了，所以不适合调整”

* “这样写修改最少”

* “当前调用方刚好只需要这些字段”



这些都不能证明当前设计本身是合理的。



但是必须识别并遵守当前仍然成立的客观系统约束，包括但不限于：



* 外部协议

* 公开 API 兼容性

* 框架契约

* 线程模型

* 性能要求

* 数据兼容性

* 持久化格式

* 跨系统依赖

* 已明确的业务规则



第一性原理要求重新审视设计本身，而不是忽略系统赖以成立的客观边界。



### 避免测试驱动开发（TDD）



兜底和测试是糟糕设计的补丁，一个足够优秀、结构自洽、边界清晰且遵循正确约束的系统，其正确性应当主要来自设计本身，而不是依赖大量测试和防御性代码来兜底。



****不得以测试为中心****（TDD）的思维方式驱动代码设计和实现。这意味着你可能从一开始就将注意力放在如何让这个已被默认不合理、不自洽的系统去通过测试代码，而不是如何去真正设计一个合理、自洽的系统上。测试应当用于验证设计和实现的正确性，而不是反过来决定系统应该如何设计。



同时，****尽可能避免防御性编程****。不必要的防御性代码，往往意味着在设计阶段没有充分理解业务规则和边界条件。这不仅会使程序架构变得臃肿，增加代码的理解和维护成本，还可能让其他开发者或 AI 将这些额外的判断和处理逻辑误认为是必要的业务规则，从而引入错误的、不必要的业务假设。



具体的禁止行为包括：



* 不得&#x4EE5;****编写测试代码并确保测试通过****&#x4F5C;为唯一或首要的编程目标。

* 不得忽视业务建模和设计合理性（具体准则可参考本 Skill 的其他正文），仅以满足需求或通过测试为目标直接编写代码。

* 不得将测试代码作为验证程序是否正常工作的手段。开发过程中可以按需编写测试代码，辅助验证接口调用、网络请求、框架行为及组件协作，但这类验证不应持久化归档为正式的测试代码。****测试代码应当且仅应当用于验证业务逻辑、业务规则和算法的准确性****，而不是为了验证程序各层能否正常工作而引入大量 Mock、Stub 和复杂的测试环境。

* 不得未经必要性分析就引入防御性编程。当需要增加额外的条件判断、异常处理、状态检查或兜底逻辑时，应当优先审视现有设计是否存在不合理、边界不清晰或逻辑不自洽的问题。

* 不得为了应对不符合当前业务约束的理论性场景而随意增加额外逻辑。所有防御性处理都应当有明确的业务依据或真实的外部风险依据。



### 架构评判准则



在下文中，我们约&#x5B9A;****逻辑单元****&#x4E3A;程序中****用于完成某一个特定任务的、逻辑内聚的黑盒****。



逻辑单元与底层实现形式无关，可以是：



* 代码块

* 函数

* 类

* 包

* 模块

* 子项目

* 微服务

* 系统



每一个逻辑单元又可以由更小颗粒度的逻辑单元组成。



下文提到的语义化编程、无二义性、设计一致性等原则在底层上具有共同目标，即：



> ****尽可能降低开发者理解、使用和修改系统时需要额外记忆的隐性规则，使系统本身形成一个自洽、稳定且可预测的语义模型。****



#### 语义化编程



满&#x8DB3;****代码即文档****&#x7684;要求。



避免依赖隐性的约定逻辑，在尽量减少额外注释与设计文档的前提下，仍然保证代码自身携带完整的业务语义。



相比代码字符数量上的简洁，更优先保障代码的可读性和语义完整性。



例如：



* 合理使用类型系统表达业务约束

* 合理使用 `@NonNull`、`@Nullable` 等表达可空性

* 使用具有业务意义的类型或类型别名代替裸 `String`、`Map`

* 对可能不存在的数据，通过返回类型、变量命名明确体现其语义

* 避免依赖调用顺序、隐含状态和约定值表达业务含义



#### 无二义性



每一个粒度的逻辑单元都应能够被拆分为多个：



* 边界清晰

* 逻辑内聚

* 职责正交



的子逻辑单元。



同一个粒度下，不应同时存在多个职责事实上重叠、但又无法精确定义差异的逻辑单元。



对于每一个逻辑单元，应当能够给出****严谨、精确且尽可能唯一的职责定义****。



该逻辑单元下的所有子逻辑单元都必须满足父逻辑单元的职责定义：



* 不超出其职责边界

* 不引入与父单元语义无关的能力

* 不破坏父单元原本建立的抽象



如果无法明确解释两个逻辑单元为什么需要同时存在，则应将其视为潜在设计问题。



#### 设计一致性



同一个逻辑单元下具有类似职责的子逻辑单元，应按照统一的设计范式和接口约定实现。



除非存在明确的业务语义差异，否则不应当为某一个 Corner Case、某一个调用方或者某一个临时需求建立例外路径。



系统整体设计的一致性优先于局部实现便利性。



#### 影响扩散的优先级



设计问题的重要程度不仅取决于问题本身，还取决于其****影响扩散范围****。



应当优先关注：



* 公共领域模型

* 公共基础组件

* 公共接口

* SPI / API

* public 类与 public 函数

* 跨模块共享协议

* 跨服务协议



因为这些逻辑单元会将自身设计直接扩散给所有调用者。



如果一个逻辑单元仅在父逻辑单元内部私有使用，其设计问题通常具有更低的扩散优先级。



问题处理时，应根据实际影响范围判断优先级，而不是简单按照文件大小或修改难度排序。



### 可理解系统



对于设计良好的系统，应当尽可能仅凭不同逻辑单元对外暴露的协议定义，例如：



* 模块名称

* package 名称

* 类型名称

* 接口

* 抽象类

* 函数签名

* 数据结构

* 模块依赖关系



就能够逐步建立对系统整体架构的理解。



如果必须阅读大量实现细节才能理解某个模块究竟承担什么职责，本身就意味着该逻辑单元可能没有建立足够清晰的抽象边界。



本 Skill 的侧重点是系统设计与代码表达，而非安全性、性能等其他维度。



分析过程中可以记录发现的安全问题、性能问题或业务 Bug，但除非它们直接阻碍当前重构工作的正确性，否则不得擅自扩大任务范围进行修复。



## 问题评判标准



可以参考 Martin Fowler《Refactoring》中定义的代码坏味道判断函数级、代码块级逻辑单元的问题。



但传统代码坏味道主要集中在细粒度代码实现，因此还必须检查：



* 系统架构

* 模块职责

* 模块依赖

* 领域模型

* 数据结构

* 公共接口

* 状态模型

* 生命周期

* 并发模型

* 错误模型

* 资源所有权

* 实现范式



等更加宏观的设计问题。



### 自洽性优先于简洁性，整体最优大于局部最优



****系统整体的设计自洽性始终优先于局部实现的简洁性、便利性和针对当前调用场景的最优化。****



在判断一个逻辑单元的设计时，不得仅依据当前修改点或当前调用方的需求进行****局部合理化****。



必须同时检查：



* 该逻辑单元自身的职责定义

* 父逻辑单元的设计约定

* 同级逻辑单元之间的一致性

* 当前已经形成的领域模型

* 当前已经形成的接口协议



****调用方的偶然需求不得反向定义被调用单元的职责和接口语义。****



因为设计约束导致局部代码适度复杂化，在合理范围内是可以接受的。



关键在于通过统一、自洽的设计，为开发者带来：



* 更少的歧义

* 更低的心智成本

* 更强的可预测性



例如，为了一时调用便利，将原本属于同一个处理器的业务逻辑拆分到两个职责重叠的模块，即使当前调用代码更加简单，也会增加开发者理解二者差异的成本。



反过来，将两个具有明确不同语义边界的逻辑强行合并，同样属于设计问题。



如果 `loadScript` 和 `loadConfig` 在语义上都承担“加载并返回文档信息”的职责，则原则上应采用相同的结果结构，而不能因为某一个调用方暂时只使用部分信息，就反向改变底层接口语义。



### 领域概念的唯一规范表达



在同一个逻辑边界内，同一个领域概念原则上应存在唯一的规范表示方式，即 Canonical Representation。



不应同时使用多个语义等价但结构不同的数据类型、参数格式或返回结构表达同一个概念。



例如，如果：



* `String`

* `URI`

* `DocumentUri`

* `FileId`



事实上都在表达完全相同的“文件身份”，则需要判断系统是否缺少统一的文件身份模型。



如果多个表示确实存在，应当能够明确说明它们之间的业务语义差异。



不同表示之间的转换应当尽可能发生在明确的职责边界处，而不是让表示差异扩散到整个系统。



### 精确、精简地定义



函数、变量、类、包、模块和项目的命名应当精确表达对应逻辑单元的职责。



命名既不能过于粗略，例如：



* `handle`

* `process`

* `manager`

* `doSomething`



导致语义丢失；



也不能为了包含全部实现细节而变得冗长复杂。



命名应描述逻辑单元****是什么或者负责什么****，而不是机械描述实现过程。



### 职责边界



一个逻辑单元内部的一切行为，都不应超出该逻辑单元的职责定义。



如果一个逻辑单元必须长期承担职责定义之外的行为，则应重新判断：



* 当前定义是否错误

* 是否需要重新命名

* 是否需要拆分

* 是否存在职责错误放置



例如，如果 `app` 模块被定义为网络应用层，则底层领域算法不应被放入其中。



如果某个模块负责领域算法实现，则 Servlet、网络协议、依赖注入等重框架逻辑通常不应反向侵入该模块。



### 接口约定对齐



当同一个逻辑单元存在多个相似接口时，应当检查这些接口是否遵循统一的协议。



包括但不限于：



* 参数类型

* 参数顺序

* 返回结构

* 可空语义

* 错误表达

* 异步模型

* 生命周期语义

* URI / ID 表示方式



例如整个 `FileSystem` 如果已经确立：



* 文件身份统一使用 `MyURI`

* 文件信息统一使用 `MyFileMetadata`

* 查询失败统一用 nullable 表达

* URI 统一位于第一个参数



则新增和修改接口时必须遵循该约定。



如果判断现有约定本身不合理，应当将其提升为整体接口设计问题，而不是为当前函数建立新的例外。



### 实现约定对齐



多个逻辑单元在处理相同任务时，应优先使用系统中已经形成的统一实现模式。



例如整个项目已经统一通过：



`storage.lockDocument { ... }`



表达文档加锁生命周期时，新代码不应当再次手工实现一套锁获取、异常处理和释放流程。



如果已有实现模式本身存在设计问题，应当修改统一抽象，而不是同时保留多套实现范式。



### 合理的抽象和复用



抽象的主要依据应当是****共享语义****，而不仅仅是代码文本相似。



当多个位置重复出现具有相同：



* 业务语义

* 生命周期

* 状态约束

* 错误语义

* 并发约束



的实现时，应当评估是否应收束为统一逻辑单元。



重复次数可以作为检查信号，但不得仅根据重复次数决定是否抽象。



当拥有完整语义的大块实现重复出现三次及以上时，应默认将其加入问题候选列表进行检查。



### 合理使用链式调用



传统代码块在同一个作用域混合大量：



* `for`

* `while`

* `if`

* `switch`

* 中间变量



时，代码块之间的逻辑边界可能变得不清晰。



对于连续的数据转换，可以考虑通过链式调用或者 Fluent API 将整个处理过程内聚为一个语义完整的表达。



同时通过最终变量命名表达整个转换结果的业务含义。



但是不得为了追求链式风格而制造：



* 难以调试的超长调用链

* 隐藏副作用

* 难以表达分支语义的嵌套 lambda

* 比传统流程控制更难理解的代码



### 积极使用不可变变量和不可变对象



可变状态会扩大开发者判断程序行为时需要考虑的时间范围和影响范围。



对于被多个逻辑单元共享的可变对象，调用者必须额外考虑：



* 谁能够修改它

* 什么时候会修改

* 修改是否影响其他引用方

* 当前读取到的是哪个时间点的状态



因此，在不存在明确状态变更语义的情况下，应优先：



* 使用不可变变量

* 使用不可变对象

* 构造时完整初始化

* 通过新对象表达状态变化



而不是采用空对象构造后逐字段修改等方式。



不可变设计并不能消除所有影响传播，但通常可以显著缩小状态变化的影响范围。



### 控制副作用



应优先使用无外部副作用的函数表达纯数据转换。



纯函数通常具有以下特征：



* 不修改函数作用域之外的状态

* 不依赖不可见的可变全局状态

* 相同输入在相同环境下得到相同输出



纯函数与“幂等”不是同一个概念，不应混淆。



网络通信、持久化、缓存、状态机、资源管理等场景天然可能需要副作用，因此不得机械要求所有函数都转化为纯函数。



对于必要副作用，应重点检查：



1. 副作用是否确实属于当前逻辑单元职责

1. 副作用是否对调用者显式可知

1. 副作用的影响范围是否被最小化

1. 状态所有权是否唯一明确

1. 生命周期是否能够在当前或明确上级逻辑单元中闭环



隐式修改全局状态、静态变量、ThreadLocal、共享缓存、对象字段等行为应当重点审查。



### 避免为了改动而改动



传统代码坏味道只是设计问题的参考，而不是必须机械执行的规则。



例如将一个大函数强行拆成多个小函数，不一定提高可读性。



如果拆分出的函数：



* 只被调用一次

* 不表达新的业务概念

* 不形成独立抽象

* 迫使开发者频繁跳转阅读



那么这种拆分可能反而破坏原本代码逻辑的连续性。



在这种情况下，可能更适合：



* 通过局部代码块建立边界

* 使用语义明确的局部变量

* 使用链式数据转换

* 重新组织流程结构



重构必须服务于语义清晰，而不是服务于某一种固定代码形式。



### 依据逻辑单元写注释



注释用于补充****代码自身无法自然表达的设计意图****，而不是重复代码已经表达的事实。



在现有逻辑单元无法完整表达业务语义时，例如：



* 特殊业务规则

* Corner Case

* 外部协议限制

* 反直觉实现

* 非显然性能约束

* 必须保持的兼容行为



可以通过注释补充“为什么必须这样实现”。



应优先通过：



* 命名

* 类型

* 接口

* 数据结构

* 逻辑单元边界



表达“代码在做什么”。



不得为了满足形式要求机械地为每一行或每一个代码块补充注释。



## 权限边界和最终责任人



系统的最终责任人仍然是人类。



因此严禁在无法自行闭环验证修改前后一致性时，仅根据自己的设计偏好擅自进行架构修改。



如果当前粒度的重构无法通过回归测试或其他可靠方式验证修改前后的：



* 对外协议

* 业务语义

* 可观察行为



符合预期，则必须经过调用者许可后才能进行实际修改。



对于当前定义不明确的逻辑单元，同样禁止擅自建立新的架构定义。



对于职责交叉、边界模糊或者存在多个合理设计方向的问题，应当交由人类架构师完成最终决策。



你可以提出自己的推荐方案，并指出调用者方案可能存在的问题，但不得将自己的推荐方案自动视为最终架构定义。



任何情况下，都不允许对代码进行设计或逻辑修改而不通知调用者。



### 第一级：自主修改



只有同时满足以下条件的问题才允许自主修改：



1. 修改方向不存在实质架构取舍，能够从现有设计中得到唯一或明显更优的答案

1. 修改影响能够封闭在当前逻辑单元内部

1. 不改变该逻辑单元向父逻辑单元暴露的职责、协议和业务语义

1. 存在充分的自动化验证手段证明修改前后的外部可观察行为符合预期



例如：



* 明确错误的访问修饰符

* 无引用且无反射使用的幽灵 private 函数

* 明显可以收窄作用域的变量

* 不改变语义的局部命名修正



如果无法满足任意一个条件，应降低为第二级或第三级。

* 公共接口

* 数据结构

* 领域模型

* 模块结构

* 生命周期

* 状态语义

* 外部行为
