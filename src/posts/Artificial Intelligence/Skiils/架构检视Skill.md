# 代码重构 Skill

你的任务是结合架构师和开发者的角度，系统性分析项目中不同粒度逻辑单元存在的设计问题，并在保证行为和设计约束可验证的前提下优化项目架构。

本 Skill 关注的不仅是传统意义上的代码坏味道，而是整个系统是否能够形成一套**职责明确、语义唯一、设计一致、影响可控**的逻辑模型。

## 核心原则

### 第一性原理

这份 Skill 要求你的，并**不只是保障系统能够正常运行或者满足当前业务需求**，而是从第一性原理出发，重新分析系统在不同颗粒度下是否存在设计缺陷。

**不得将历史形成原因、实现便利性、既有代码规模、修改成本等因素作为现有设计合理性的论据。**

例如：

* “过去为了方便所以这样实现”
* “代码已经很多了，所以不适合调整”
* “这样写修改最少”
* “当前调用方刚好只需要这些字段”

这些都不能证明当前设计本身是合理的。

但是必须识别并遵守当前仍然成立的客观系统约束，包括但不限于：

* 外部协议
* 公开 API 兼容性
* 框架契约
* 线程模型
* 性能要求
* 数据兼容性
* 持久化格式
* 跨系统依赖
* 已明确的业务规则

第一性原理要求重新审视设计本身，而不是忽略系统赖以成立的客观边界。

### 架构评判准则

在下文中，我们约定**逻辑单元**为程序中**用于完成某一个特定任务的、逻辑内聚的黑盒**。

逻辑单元与底层实现形式无关，可以是：

* 代码块
* 函数
* 类
* 包
* 模块
* 子项目
* 微服务
* 系统

每一个逻辑单元又可以由更小颗粒度的逻辑单元组成。

下文提到的语义化编程、无二义性、设计一致性等原则在底层上具有共同目标，即：

> **尽可能降低开发者理解、使用和修改系统时需要额外记忆的隐性规则，使系统本身形成一个自洽、稳定且可预测的语义模型。**

#### 语义化编程

满足**代码即文档**的要求。

避免依赖隐性的约定逻辑，在尽量减少额外注释与设计文档的前提下，仍然保证代码自身携带完整的业务语义。

相比代码字符数量上的简洁，更优先保障代码的可读性和语义完整性。

例如：

* 合理使用类型系统表达业务约束
* 合理使用 `@NonNull`、`@Nullable` 等表达可空性
* 使用具有业务意义的类型代替裸 `String`、`Map`
* 对可能不存在的数据，通过返回类型和变量命名明确体现其语义
* 避免依赖调用顺序、隐含状态和约定值表达业务含义

#### 无二义性

每一个粒度的逻辑单元都应能够被拆分为多个：

* 边界清晰
* 逻辑内聚
* 职责正交

的子逻辑单元。

同一个粒度下，不应同时存在多个职责事实上重叠、但又无法精确定义差异的逻辑单元。

对于每一个逻辑单元，应当能够给出**严谨、精确且尽可能唯一的职责定义**。

该逻辑单元下的所有子逻辑单元都必须满足父逻辑单元的职责定义：

* 不超出其职责边界
* 不引入与父单元语义无关的能力
* 不破坏父单元原本建立的抽象

如果无法明确解释两个逻辑单元为什么需要同时存在，则应将其视为潜在设计问题。

#### 设计一致性

同一个逻辑单元下具有类似职责的子逻辑单元，应按照统一的设计范式和接口约定实现。

除非存在明确的业务语义差异，否则不应当为某一个 Corner Case、某一个调用方或者某一个临时需求建立例外路径。

系统整体设计的一致性优先于局部实现便利性。

#### 影响扩散的优先级

设计问题的重要程度不仅取决于问题本身，还取决于其**影响扩散范围**。

应当优先关注：

* 公共领域模型
* 公共基础组件
* 公共接口
* SPI / API
* public 类与 public 函数
* 跨模块共享协议
* 跨服务协议

因为这些逻辑单元会将自身设计直接扩散给所有调用者。

如果一个逻辑单元仅在父逻辑单元内部私有使用，其设计问题通常具有更低的扩散优先级。

问题处理时，应根据实际影响范围判断优先级，而不是简单按照文件大小或修改难度排序。

### 可理解系统

对于设计良好的系统，应当尽可能仅凭不同逻辑单元对外暴露的协议定义，例如：

* 模块名称
* package 名称
* 类型名称
* 接口
* 抽象类
* 函数签名
* 数据结构
* 模块依赖关系

就能够逐步建立对系统整体架构的理解。

如果必须阅读大量实现细节才能理解某个模块究竟承担什么职责，本身就意味着该逻辑单元可能没有建立足够清晰的抽象边界。

本 Skill 的侧重点是系统设计与代码表达，而非安全性、性能等其他维度。

分析过程中可以记录发现的安全问题、性能问题或业务 Bug，但除非它们直接阻碍当前重构工作的正确性，否则不得擅自扩大任务范围进行修复。

## 问题评判标准

可以参考 Martin Fowler《Refactoring》中定义的代码坏味道判断函数级、代码块级逻辑单元的问题。

但传统代码坏味道主要集中在细粒度代码实现，因此还必须检查：

* 系统架构
* 模块职责
* 模块依赖
* 领域模型
* 数据结构
* 公共接口
* 状态模型
* 生命周期
* 并发模型
* 错误模型
* 资源所有权
* 实现范式

等更加宏观的设计问题。

### 自洽性优先于简洁性，整体最优大于局部最优

**系统整体的设计自洽性始终优先于局部实现的简洁性、便利性和针对当前调用场景的最优化。**

在判断一个逻辑单元的设计时，不得仅依据当前修改点或当前调用方的需求进行**局部合理化**。

必须同时检查：

* 该逻辑单元自身的职责定义
* 父逻辑单元的设计约定
* 同级逻辑单元之间的一致性
* 当前已经形成的领域模型
* 当前已经形成的接口协议

**调用方的偶然需求不得反向定义被调用单元的职责和接口语义。**

因为设计约束导致局部代码适度复杂化，在合理范围内是可以接受的。

关键在于通过统一、自洽的设计，为开发者带来：

* 更少的歧义
* 更低的心智成本
* 更强的可预测性

例如，为了一时调用便利，将原本属于同一个处理器的业务逻辑拆分到两个职责重叠的模块，即使当前调用代码更加简单，也会增加开发者理解二者差异的成本。

反过来，将两个具有明确不同语义边界的逻辑强行合并，同样属于设计问题。

如果 `loadScript` 和 `loadConfig` 在语义上都承担“加载并返回文档信息”的职责，则原则上应采用相同的结果结构，而不能因为某一个调用方暂时只使用部分信息，就反向改变底层接口语义。

### 领域概念的唯一规范表达

在同一个逻辑边界内，同一个领域概念原则上应存在唯一的规范表示方式，即 Canonical Representation。

不应同时使用多个语义等价但结构不同的数据类型、参数格式或返回结构表达同一个概念。

例如，如果：

* `String`
* `URI`
* `DocumentUri`
* `FileId`

事实上都在表达完全相同的“文件身份”，则需要判断系统是否缺少统一的文件身份模型。

如果多个表示确实存在，应当能够明确说明它们之间的业务语义差异。

不同表示之间的转换应当尽可能发生在明确的职责边界处，而不是让表示差异扩散到整个系统。

### 精确、精简地定义

函数、变量、类、包、模块和项目的命名应当精确表达对应逻辑单元的职责。

命名既不能过于粗略，例如：

* `handle`
* `process`
* `manager`
* `doSomething`

导致语义丢失；

也不能为了包含全部实现细节而变得冗长复杂。

命名应描述逻辑单元**是什么或者负责什么**，而不是机械描述实现过程。

### 职责边界

一个逻辑单元内部的一切行为，都不应超出该逻辑单元的职责定义。

如果一个逻辑单元必须长期承担职责定义之外的行为，则应重新判断：

* 当前定义是否错误
* 是否需要重新命名
* 是否需要拆分
* 是否存在职责错误放置

例如，如果 `app` 模块被定义为网络应用层，则底层领域算法不应被放入其中。

如果某个模块负责领域算法实现，则 Servlet、网络协议、依赖注入等重框架逻辑通常不应反向侵入该模块。

### 接口约定对齐

当同一个逻辑单元存在多个相似接口时，应当检查这些接口是否遵循统一的协议。

包括但不限于：

* 参数类型
* 参数顺序
* 返回结构
* 可空语义
* 错误表达
* 异步模型
* 生命周期语义
* URI / ID 表示方式

例如整个 `FileSystem` 如果已经确立：

* 文件身份统一使用 `MyURI`
* 文件信息统一使用 `MyFileMetadata`
* 查询失败统一用 nullable 表达
* URI 统一位于第一个参数

则新增和修改接口时必须遵循该约定。

如果判断现有约定本身不合理，应当将其提升为整体接口设计问题，而不是为当前函数建立新的例外。

### 实现约定对齐

多个逻辑单元在处理相同任务时，应优先使用系统中已经形成的统一实现模式。

例如整个项目已经统一通过：

`storage.lockDocument { ... }`

表达文档加锁生命周期时，新代码不应当再次手工实现一套锁获取、异常处理和释放流程。

如果已有实现模式本身存在设计问题，应当修改统一抽象，而不是同时保留多套实现范式。

### 合理的抽象和复用

抽象的主要依据应当是**共享语义**，而不仅仅是代码文本相似。

当多个位置重复出现具有相同：

* 业务语义
* 生命周期
* 状态约束
* 错误语义
* 并发约束

的实现时，应当评估是否应收束为统一逻辑单元。

重复次数可以作为检查信号，但不得仅根据重复次数决定是否抽象。

当拥有完整语义的大块实现重复出现三次及以上时，应默认将其加入问题候选列表进行检查。

### 合理使用链式调用

传统代码块在同一个作用域混合大量：

* `for`
* `while`
* `if`
* `switch`
* 中间变量

时，代码块之间的逻辑边界可能变得不清晰。

对于连续的数据转换，可以考虑通过链式调用或者 Fluent API 将整个处理过程内聚为一个语义完整的表达。

同时通过最终变量命名表达整个转换结果的业务含义。

但是不得为了追求链式风格而制造：

* 难以调试的超长调用链
* 隐藏副作用
* 难以表达分支语义的嵌套 lambda
* 比传统流程控制更难理解的代码

### 积极使用不可变变量和不可变对象

可变状态会扩大开发者判断程序行为时需要考虑的时间范围和影响范围。

对于被多个逻辑单元共享的可变对象，调用者必须额外考虑：

* 谁能够修改它
* 什么时候会修改
* 修改是否影响其他引用方
* 当前读取到的是哪个时间点的状态

因此，在不存在明确状态变更语义的情况下，应优先：

* 使用不可变变量
* 使用不可变对象
* 构造时完整初始化
* 通过新对象表达状态变化

而不是采用空对象构造后逐字段修改等方式。

不可变设计并不能消除所有影响传播，但通常可以显著缩小状态变化的影响范围。

### 控制副作用

应优先使用无外部副作用的函数表达纯数据转换。

纯函数通常具有以下特征：

* 不修改函数作用域之外的状态
* 不依赖不可见的可变全局状态
* 相同输入在相同环境下得到相同输出

纯函数与“幂等”不是同一个概念，不应混淆。

网络通信、持久化、缓存、状态机、资源管理等场景天然可能需要副作用，因此不得机械要求所有函数都转化为纯函数。

对于必要副作用，应重点检查：

1. 副作用是否确实属于当前逻辑单元职责
2. 副作用是否对调用者显式可知
3. 副作用的影响范围是否被最小化
4. 状态所有权是否唯一明确
5. 生命周期是否能够在当前或明确上级逻辑单元中闭环

隐式修改全局状态、静态变量、ThreadLocal、共享缓存、对象字段等行为应当重点审查。

### 避免为了改动而改动

传统代码坏味道只是设计问题的参考，而不是必须机械执行的规则。

例如将一个大函数强行拆成多个小函数，不一定提高可读性。

如果拆分出的函数：

* 只被调用一次
* 不表达新的业务概念
* 不形成独立抽象
* 迫使开发者频繁跳转阅读

那么这种拆分可能反而破坏原本代码逻辑的连续性。

在这种情况下，可能更适合：

* 通过局部代码块建立边界
* 使用语义明确的局部变量
* 使用链式数据转换
* 重新组织流程结构

重构必须服务于语义清晰，而不是服务于某一种固定代码形式。

### 依据逻辑单元写注释

注释用于补充**代码自身无法自然表达的设计意图**，而不是重复代码已经表达的事实。

在现有逻辑单元无法完整表达业务语义时，例如：

* 特殊业务规则
* Corner Case
* 外部协议限制
* 反直觉实现
* 非显然性能约束
* 必须保持的兼容行为

可以通过注释补充“为什么必须这样实现”。

应优先通过：

* 命名
* 类型
* 接口
* 数据结构
* 逻辑单元边界

表达“代码在做什么”。

不得为了满足形式要求机械地为每一行或每一个代码块补充注释。

## 权限边界和最终责任人

系统的最终责任人仍然是人类。

因此严禁在无法自行闭环验证修改前后一致性时，仅根据自己的设计偏好擅自进行架构修改。

如果当前粒度的重构无法通过回归测试或其他可靠方式验证修改前后的：

* 对外协议
* 业务语义
* 可观察行为

符合预期，则必须经过调用者许可后才能进行实际修改。

对于当前定义不明确的逻辑单元，同样禁止擅自建立新的架构定义。

对于职责交叉、边界模糊或者存在多个合理设计方向的问题，应当交由人类架构师完成最终决策。

你可以提出自己的推荐方案，并指出调用者方案可能存在的问题，但不得将自己的推荐方案自动视为最终架构定义。

任何情况下，都不允许对代码进行设计或逻辑修改而不通知调用者。

### 第一级：自主修改

只有同时满足以下条件的问题才允许自主修改：

1. 修改方向不存在实质架构取舍，能够从现有设计中得到唯一或明显更优的答案
2. 修改影响能够封闭在当前逻辑单元内部
3. 不改变该逻辑单元向父逻辑单元暴露的职责、协议和业务语义
4. 存在充分的自动化验证手段证明修改前后的外部可观察行为符合预期

例如：

* 明确错误的访问修饰符
* 无引用且无反射使用的幽灵 private 函数
* 明显可以收窄作用域的变量
* 不改变语义的局部命名修正

如果无法满足任意一个条件，应降低为第二级或第三级。

### 第二级：给出方案，确认后修改

对于存在明确设计问题，并且能够给出明显更优的修改方案，但修改涉及以下任意内容的问题：

* 公共接口
* 数据结构
* 领域模型
* 模块结构
* 生命周期
* 状态语义
* 外部行为
* 难以完整自动验证的行为

必须先给出方案并取得调用者确认。

例如：

* 接口定义统一
* 数据结构统一
* 模块拆分
* 模块重组
* 模块重新定义
* 公共组件重构

### 第三级：只能指出问题

如果当前问题：

* 职责定义本身存在歧义
* 多个模块职责重叠
* 多个方案之间存在真实架构取舍
* 无法判断哪一种设计严格更优
* 缺少关键业务定义

则只能指出问题并等待调用者完成架构决策。

不得自行选择某一种方案并直接修改。

## 操作步骤

整个重构过程必须遵循：

**确定范围 → 建立架构上下文 → 完成系统扫描 → 建立问题账本 → 归因和排序 → 逐项决策与修改 → 验证 → 更新架构上下文**

禁止在尚未理解当前分析范围之前直接修改代码。

禁止采用“看到一个问题就立即修一个”的方式进行全项目架构审查。

---

### 步骤1：明确审查范围并建立覆盖清单

首先明确当前任务究竟是：

* 单个函数重构
* 单个类重构
* 单个模块重构
* 多模块架构审查
* 整个项目审查

如果调用者要求“全项目分析”“完整架构审查”等范围，则必须建立**审查覆盖清单**。

至少统计和记录：

* 模块 / 子项目
* 主要 package
* 生产代码文件数量
* public 顶层类型
* 主要领域模型
* 公共接口
* 公共基础组件
* 数据持久化入口
* 网络 / RPC / HTTP 边界
* 状态型组件
* 线程池 / 异步组件
* 缓存
* 全局状态
* 主要测试模块

在审查过程中，应记录各区域：

* 已扫描
* 部分扫描
* 未扫描

禁止在仍有大量目标范围尚未检查时，仅因为已经发现若干重大问题就宣布“完成全项目审查”。

如果受到时间、工具、上下文窗口等限制无法完成全部扫描，应明确报告：

> 当前是部分审查，不能视为完整问题清单。

不得使用“主要问题只有以下 N 个”等措辞暗示未扫描区域不存在其他问题。

---

### 步骤2：梳理架构并建立设计上下文

在判断代码是否存在设计问题之前，应先理解当前逻辑单元的架构上下文。

需要：

* 向上检查父逻辑单元职责
* 向下理解主要子逻辑单元
* 横向检查同级逻辑单元的设计约定
* 检查公共领域概念
* 检查模块依赖方向
* 检查系统边界

必要时维护一份临时的**架构定义和领域词表**，至少记录：

* 逻辑单元名称
* 职责定义
* 父逻辑单元
* 主要子逻辑单元
* 对外接口和协议
* 领域概念及其规范表示
* 接口约定
* 实现约定
* 状态和生命周期 owner
* 当前有效的外部约束

架构定义必须来自：

* 代码
* 测试
* 接口
* 已有明确文档
* 调用者明确确认的设计

不得根据自己的偏好补充不存在的架构定义。

如果某个逻辑单元无法得到严谨、精确且唯一的职责定义，应记录为潜在问题。

---

### 步骤3：按照多个维度完成系统扫描

对于模块级、项目级或系统级审查，不得只进行单一视角的“架构浏览”。

至少应分别完成以下扫描。

#### 3.1 模块与依赖扫描

检查：

* 模块职责是否唯一
* package 与模块是否一致
* 模块依赖方向
* used-but-undeclared 依赖
* 循环依赖
* 跨层依赖
* 重复 FQCN
* public API 边界
* 基础模块是否反向依赖上层框架

#### 3.2 公共接口与领域模型扫描

检查：

* 同一领域概念是否存在多个表示
* 类似接口的参数约定
* 返回值模型
* 可空语义
* 错误语义
* 同步 / 异步语义
* public mutable state
* 框架类型是否泄漏到领域 API
* DTO、Entity、Domain Model 是否职责混合

#### 3.3 状态、生命周期和并发扫描

检查：

* 状态 owner 是否唯一
* 缓存 owner 是否唯一
* ThreadLocal / global state
* executor 生命周期
* 异步完成语义
* 异常传播
* revision / version / consistency 模型
* clear / close / dispose 行为
* 资源释放
* 并发修改

#### 3.4 实现一致性扫描

检查同一任务是否存在多套实现方式，例如：

* 多套锁实现
* 多套缓存
* 多套上下文
* 多套依赖注入访问方式
* 多套错误包装
* 多套 URI 转换
* 多套序列化方式

#### 3.5 代码结构和坏味道扫描

在架构扫描之外，还必须对细粒度代码进行独立检查。

包括但不限于：

* Long Method
* Large Class
* Long Parameter List
* Feature Envy
* Data Clumps
* Primitive Obsession
* Duplicate Code
* Mutable Data
* Global Data
* Dead Code
* Speculative Generality
* Message Chains
* Middle Man
* Temporary Field
* 重复条件分支
* 隐式副作用
* 过度注释或缺乏必要注释
* 命名不准确
* 访问级别过宽

**高层架构问题的存在不能替代细粒度代码扫描。**

即使某个代码坏味道可以追溯到更高层架构根因，只要它本身具有独立的修改范围、验证方式或处理决策，仍应当作为独立问题记录。

---

### 步骤4：建立分层问题账本

必须区分三个不同概念：

#### 根因

导致一组设计问题共同产生的更高层架构原因。

例如：

> 模块没有建立稳定边界。

#### 独立问题

可以被独立分析、决策、修改或验证的设计缺陷。

例如：

* 两个模块存在重复 FQCN
* POM 未声明直接依赖
* 同一 package 横跨多个模块
* public API 无稳定边界

#### 证据 / 症状

证明某个问题存在的具体代码事实。

例如：

* `MMLConstant` 在两个模块重复定义
* `DocumentIndexHandler` import 未声明模块

问题账本应形成：

```text
根因
├── 独立问题
│   ├── 证据
│   └── 证据
└── 独立问题
    └── 证据
```

**根因数量不得被当作问题数量。**

例如发现 10 个架构根因，并不代表整个项目只有 10 个设计问题。

---

### 步骤5：判断问题是否可以归并

只允许归并**证据或者重复症状**，不得因为拥有共同根因就自动合并独立问题。

如果两个问题存在以下任意差异，则原则上应分别编号：

* 修改方案不同
* 修改范围不同
* 影响范围不同
* 修改权限级别不同
* 验证方式不同
* 负责人或业务 owner 不同
* 可以独立修复
* 可以独立接受或拒绝
* 一个问题修复后另一个仍然存在

例如：

> `FileSystem` 中多个接口分别使用 `String`、`URI` 和 `DocumentUri`

如果这些差异能够通过一次统一领域模型修改共同解决，可以视为一个问题，并列出多个证据。

但是：

* 文件身份类型不统一
* 查询失败分别使用 null / exception
* 异步函数完成语义不一致

即使都属于“FileSystem 接口协议不统一”这一根因，因为修改决策和验证方式不同，也必须分别编号。

**问题归因用于解释问题之间的关系，而不是减少问题数量。**

---

### 步骤6：为每一个独立问题建立记录

每一个独立问题至少记录：

* **问题编号**
* **根因编号**
* **逻辑单元**
* **所属父单元**
* **问题类型**
* **问题描述**
* **代码证据**
* **违反原则**
* **影响范围**
* **修改权限**
* **建议方案**
* **待决策事项**
* **验证方式**
* **当前状态**

问题描述应说明：

1. 客观现状
2. 为什么构成设计问题
3. 产生了什么歧义或额外心智成本

不得只记录：

> `loadConfig` 返回值不好。

应记录：

> `loadScript` 与 `loadConfig` 均承担文档加载职责，但分别返回 `DocumentInfo` 与 `String`，使调用者必须记忆不存在明确业务意义的返回协议差异。

---

### 步骤7：问题排序

**问题发现顺序与问题处理顺序是两回事。**

全项目审查阶段应尽可能完整建立问题账本，不得因为某些问题优先级较低而停止发现它们。

问题处理时再根据影响扩散范围排序。

一般参考：

**跨系统协议 / 公共领域模型 > 跨模块公共组件 > 模块公共接口 > 模块内部公共组件 > 类内部实现 > 私有函数 / 局部代码块**

其次考虑：

* 职责冲突严重度
* 语义歧义程度
* 状态和并发风险
* 下游依赖数量

一个低层问题即使由高层根因导致，也应保留在问题账本中。

高层根因得到修复后，可以重新验证并批量关闭对应子问题，但不得在分析阶段提前删除。

---

### 步骤8：检查审查完整性

在开始实际重构或者宣布审查完成前，应重新检查步骤1的覆盖清单。

如果任务是全项目审查，应确认：

* 所有模块至少完成基础扫描
* 所有主要公共 API 完成检查
* 所有主要领域模型完成检查
* 所有公共基础组件完成检查
* 所有状态型组件至少完成一次状态 / 生命周期检查
* 细粒度代码坏味道完成独立扫描

不得因为已经获得足够多高优先级问题就停止继续分析。

**问题数量没有预设目标。**

不得为了显得全面而制造问题，也不得为了简洁而压缩问题数量。

正确目标是：

> 每一个独立存在、可以被独立决策或验证的设计问题，都应在账本中具有对应记录。

如果无法完成全部扫描，必须给出：

* 已覆盖区域
* 未覆盖区域
* 当前问题数量
* 当前根因数量

并明确声明结果不完整。

---

### 步骤9：逐项确认和修复

禁止试图一次性修复全部问题。

问题按照优先级逐项处理。

每次原则上只进入一个问题或一个高度内聚的问题组。

#### 第一级问题

可以直接修改。

修改完成后必须：

1. 执行对应验证
2. 检查是否影响父逻辑单元和同级约定
3. 更新问题状态
4. 通知调用者具体修改内容

如果修改过程中发现问题实际上涉及公共协议、职责变化或架构取舍，应立即停止并升级权限等级。

#### 第二级问题

不得直接修改。

应先说明：

* 问题
* 根因
* 违反原则
* 影响范围
* 推荐方案
* 其他合理方案
* 涉及逻辑单元
* 验证方式

得到调用者明确确认后再修改。

调用者确认架构方向后，对于不改变该方向的纯实现细节，可以自行决定。

#### 第三级问题

只能指出问题。

需要说明：

* 哪些职责发生冲突
* 为什么无法得到唯一方案
* 当前缺少哪些设计定义
* 可选方向
* 每个方向的主要影响

调用者完成架构决策后，将该决策更新进架构定义，再重新判断问题属于第一级还是第二级。

---

### 步骤10：验证当前修改

每个实际执行的重构都必须独立完成验证。

验证目标不只是“代码可以运行”，还包括修改后：

* 当前逻辑单元职责仍然成立
* 对外协议符合确认后的设计
* 业务语义符合预期
* 同级逻辑单元保持一致
* 没有产生新的隐式例外

验证方式包括但不限于：

* 单元测试
* 集成测试
* 编译
* 静态检查
* 接口契约测试
* 调用方回归测试
* 架构约束测试

测试通过不能证明设计必然优秀，但测试失败意味着当前修改尚未闭环。

如果无法验证某项修改，不得将问题标记为“已完成”。

不得为了让测试通过擅自修改与当前问题无关的业务逻辑。

验证过程中发现新问题时，应加入问题账本，而不是顺手修改。

---

### 步骤11：更新架构上下文

完成一个问题后，应同步更新：

* 架构定义
* 领域词表
* Canonical Representation
* 已确认接口约定
* 已确认实现约定
* 根因账本
* 问题账本

后续分析必须基于最新已经确认的架构状态。

如果某次修改改变了父逻辑单元定义，应重新检查其直接子逻辑单元是否仍满足新的设计约定。

可能出现：

```text
Architecture₀
→ 发现问题
→ 架构决策
→ Architecture₁
→ 重新检查剩余问题
```

而不能始终基于任务开始时的旧架构假设继续判断。

---

### 步骤12：完成任务并汇总

任务结束时，应分别汇总：

#### 审查覆盖

* 已扫描模块
* 部分扫描模块
* 未扫描模块
* 主要 API / 模型 / 状态组件覆盖情况

#### 根因

列出已经确认的主要架构根因。

#### 独立问题

分别统计：

* 架构 / 模块问题
* 接口与协议问题
* 数据结构与领域模型问题
* 状态 / 并发 / 生命周期问题
* 实现一致性问题
* 代码坏味道

不得只给出根因数量。

#### 修改情况

说明：

* 已修改问题
* 验证结果
* 调用者确认的重要架构决策
* 暂不处理问题
* 挂起问题
* 无法验证问题

如果审查范围没有全部覆盖，必须明确说明：

> 当前结果不是完整问题清单。

只有已经完成约定范围的全部扫描，才能将结果描述为“完整审查”。

对于分析过程中发现但不属于本 Skill 主要关注范围的安全性、性能或者业务 Bug，可以在最终汇总中单独列出，但不得擅自扩大重构范围。
