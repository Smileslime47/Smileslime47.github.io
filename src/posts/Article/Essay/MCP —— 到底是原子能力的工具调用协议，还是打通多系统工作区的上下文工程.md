# MCP —— 到底是原子能力的工具调用协议，还是打通多系统工作区的上下文工程

## MCP不只是原子能力的工具调用

虽然在各种新概念还在不断产生的今天（Skill、Harness、blahblah），讨论MCP这个已经有些老登了的概念显得有些过时。但是对于Agent领域，各种新技术要解决的其实都是类似的问题，我个人也曾在[这篇帖子](https://47saikyo.moe/posts/Article/Essay/AI%E4%B8%BA%E4%BD%95%E5%88%B0%E5%BA%95%E8%BF%98%E6%B2%A1%E6%9C%89%E6%9B%BF%E4%BB%A3%E4%BA%BA%E7%B1%BB%20%E2%80%94%E2%80%94%20%E5%85%B3%E4%BA%8E%E8%BD%AF%E4%BB%B6%E8%AE%BE%E8%AE%A1%E3%80%81%E8%BE%BE%E8%BE%BE%E4%B8%BB%E4%B9%89%E4%B8%8E%E4%BA%BA%E7%B1%BB%E7%9A%84%E4%B8%8D%E5%8F%AF%E6%9B%BF%E4%BB%A3%E6%80%A7)提过一个观点：**Agent如今最大的gap，或者说无法替代人类的原因，绝对是上下文的利用能力远远不及现实世界的人类，具体体现在上下文的获取途径、权重算法、Ground Truth的隐性认知等等**。所以我还是想做一些消歧义 —— MCP作为上下文工程的一环，要解决的和Skill、Harness要解决的问题并不冲突，它要解决的，实际上是**如何让Agent像人一样自由地获取和操作上下文**这一点

在工作的过程中，我发现似乎相当一部分的同事都将MCP当成了简单的工具调用协议，或者说更粗暴的，只是一种将**原子能力**暴露给Agent的接口。其实大家可能既没有研究过MCP的官方文档，也没有研究过MCP的协议具体都包含了什么东西。正好我们团队最近也在通过MCP协议来打通Agent与业务系统的工作区的边界。在讨论一切之前，我先下一个TL;DR的结论：

> **MCP的定位，并不是纯粹的工具调用协议，而是用于打通Agent的工作区与外部系统的工作区之间的上下文的协议**

对于具有连续性的业务（即用户会话）的业务系统，同样也可以面向用户当前工作会话建立一个具有完整上下文关联关系的工作区 —— 换句话说，MCP可以是**围绕原本就存在的业务系统，额外扩展出来的一套面向Agent的操作接口，让Agent能够像用户一样去全功能地操作业务系统**，客户端和服务端共同围绕一项任务建立一个完整的、持续的会话上下文，而不是只是简单地作为提供原子化的能力的孤立系统。或者也可以说，**MCP实际上是业务系统的一部分，而非Agent系统的一部分**

## 带会话的有状态通信

身边许多同事会将MCP协议当作简单的**工具调用协议**，这些人不论是生产者还是消费者，往往都只会使用MCP中的tool这一feature，大部分人都没有思考过一个问题，如果MCP要解决的只是**工具调用**这一单一的问题，简单的传统HTTP协议加上Schema足矣，但MCP仍然基于一套完整的`发起会话->能力协商->双向RPC调用->关闭会话`等流程构建了一套完整的会话生命周期

在Spring AI的[MCP一章](https://docs.spring.io/spring-ai/reference/api/mcp/mcp-overview.html)中，Stateless MCP Server也是单独作为一章出现的，这足以说明在大部分场景下，**MCP的服务端作为一个业务系统，都应当思考其到底是一个有中间状态的，具有会话概念的服务，还是一个纯粹的无状态服务**

## MCP协议

我们直接回看当前的MCP协议，MCP协议的底层架构是借鉴了LSP协议的，二者都是**基于Json-RPC消息模型的持续双向通信协议**，Json-RPC作为一个**无指向性**的双工协议，客户端和服务端都可以成为请求或通知的发起方，并不存在只能由客户端调用服务端的固定方向。在实际使用的过程中，服务端可以在协议约束的范围里，调用客户端的能力，从而完成某种**操作前台工作区**的能力。

以面向IDE场景的LSP举例，对于提供了特定编程语言语言服务的服务端，和集成了该LSP服务端的某客户端IDE，服务端有能力通过调用`textDocument/publishDiagnostics`方法向客户端推送代码检查结果（注意，这里是不需要客户端主动调用的，LSP在代码检查结果上支持客户端主动调用并接受结果的pull模式，和服务端主动推送结果的push模式），也有能力主动调用`workspace/applyEdits`方法去主动修改客户端工作区中某些文件的内容

同样地，MCP的客户端和服务端也各自拥有一系列的特性协议，并通过initialize和initialized协商各自支持的能力，这里我们只看真正面向业务的特性，而暂且不考虑initialize、ping、logging这种工具性特性

|端侧|能力|描述|
|---|---|---|
|服务端|Tools|提供工具调用的能力，Mcp Specification[官方文档](https://modelcontextprotocol.io/specification/2025-11-25/server)中列举的Example为`API POST requests, file writing`|
|服务端|Resources|提供服务端侧资源检索的能力，Mcp Specification的[官方文档](https://modelcontextprotocol.io/specification/2025-11-25/server)中列举的Example为`File contents, git history`|
|服务端|Prompts|MCP根据场景预设的提示词或工作流（这个在Skill的影响下作用被弱化了）|
|服务端|Subscriptions|订阅服务端中的某个Resource，当Resource内容变化、更新时，自动推送通知|
|客户端|Sampling|当服务端需要通过LLM完成某些目的时，借用客户端的LLM接口实现相关操作|
|客户端|Elicitation|当服务端试图对工作区执行某些操作时，向客户端（或者说用户）进行二次确认，或者补充信息|
|客户端|Roots|向服务端同步当前客户端可操作的workspace|

在2026年的[SEP-2577](https://modelcontextprotocol.io/seps/2577-deprecate-roots-sampling-and-logging?utm_source=chatgpt.com)中，以下feature被标记为弃用，进入过渡阶段
- Roots：因为客户端可以和服务端直接通过Tools/Resource等语义更强的能力来同步工作区状态
- Sampling：服务端可以直接内部集成LLM API来屏蔽相关的AI调用的底层实现
- Logging：这个不是我们要讨论的重点，主要是建议使用更成熟的可观测性库来实现

这里我特地列举了Tools和Resouce的官方举例，你发现了什么吗？
- Tools的举例是POST请求、文件写入这种明显具有副作用的函数，而非纯粹的原子化的、无副作用的纯函数能力接口
- Resource举例是文件内容、Git历史这种明显的和工作区状态强相关的动态资源，而非文档、知识库这种相对静态的资源

总的来说，根据MCP的官方文档描述，MCP的定位是用于**让Agent像人一样操作一个系统的上下文，打通传统软件工程的上下文概念与Agent的上下文概念**，这里的上下文，不只是原子能力、知识库这种静态的上下文，也包含了基于用户当前工作区会话的交互和感知的动态上下文。上下文并不是一个伴随着AI时代产生的新词汇，早在传统的软件工程时代就已出现，但是不论是软件工程还是Agent工程，上下文的含义都是**调用者（人/AI/程序）在调用系统完成某一项任务时，已经发生的事件、当前状态和即将发生的事件的条件**。而对于绝大多数AI-Enhanced系统，业务系统的上下文工程和Agent是割裂的，人通过User Interface访问业务系统，操作业务系统的上下文 —— Agent却对业务系统无从下手，于是便有了MCP这个Agent版的User Interface，用于让Agent访问业务系统，操作业务系统的上下文，并将业务系统的上下文纳入到自己的上下文工程（或者说，工作区）里。

当然我并不打算断言说，MCP天生就必须是一个有状态的微服务，但是在一个实际的业务系统中，**带副作用的非纯函数接口**通常都是一个不可避免的事情，这也是为什么我打算将MCP的工具大体上分为四大类：

- 感知（有状态上文）：用于让Agent通过MCP侧业务系统感知用户会话相关的有状态上文信息
- 交互（有状态下文）：用于让Agent操作MCP侧系统完成特定的交互目的
- 检索（无状态上文）：用于让Agent通过MCP侧业务系统数据源检索非会话相关的上下文(如知识库,模板检索等)
- 算子（无状态下文）：用于让Agent调用MCP侧业务系统的原子化的、无状态的能力，不依赖用户的会话

## 使用场景

拿我们的业务场景举例子，我们的业务场景大体上可以看做一个**面向DSL的云端IDE**，基本上可以作为云端IDE看待，除了在MCP中开放我们已经成熟的原子的领域化能力外，当然MCP的另一个核心目的也是打通Agent与IDE系统的边界，让用户能像Cursor一样操作IDE系统。

我们的做法就是先通过标准的MCP鉴权程序（针对用户使用API Key完成身份认证，并在认证后关联用户当前的业务会话），对用户信息进行认证后才能连接MCP服务端，拿到用户信息后，我们就可以和IDE服务进行通信，比如从IDE服务端尝试是否能过获取用户当前的LSP会话，来决定后续的操作

- 如果用户当前有一个正在活跃的LSP会话，则说明用户当前正在使用我们的IDE前台，则一系列关于编辑器、工作区的动态操作工具可以暴露给Agent，并开放MCP与IDE前端通信的能力（注意是MCP与前端，这里不涉及到Agent），用来展示代码编辑MCP工具的Diff相关的信息
- 反之，则说明用户在使用一个独立的Agent连接MCP，不存在一个活跃的IDE会话，则上述的相关工具要么禁用，要么切换代码逻辑，需要展示的视图不再与前端通信渲染，原本用于在前端反馈确认的工具调用则切换至`mcp/elicitation`，用于编辑器文本模型的编辑操作直接应用于服务端文件系统的持久化文件上，etc.

上面的操作都是在MCP协议支持的范围里实现，并**未绕过MCP进行任何定制化的魔改**，因此仍然保留了MCP协议本身的可迁移性。当然这里只是粗略地列了我们这边的一些场景，实际的MCP实现中要更加复杂

举一些外界的例子

- 对于有状态的MCP服务，我认识的设计师同事，通过Vibma（Figma的MCP工具），同样实现的是将Codex与自己的Figma项目工作区打通，让Codex可以直接去感知和交互当前的Figma项目
- 同样业界也有许多无状态的MCP服务，比如高德地图的MCP，主要提供的就是一系列的原子化无状态能力（路线规划、定位、天气查询等），基本上所有工具都不依赖用户会话

## User Interface

其实从这个角度来说，MCP和传统的Web前端（TypeScript）定位比较接近，因为二者都是作为一个用于操作业务系统的“**User Interface**”，只是操作者不同而已（前者为Agent，后者为人）

但是MCP和传统的Web前端又比较不太一样的点是，虽然二者均为User Interface，但是作为Web前端，人看到的是**前端代码调用后端接口，接受到响应结构体后，经过渲染得到的可视化操作界面**，人看到的并不是后端的接口，因此在设计传统的Web前后端接口时，往往是**协议约定＞可读性**的，但是对于MCP，虽然它在代码架构上类似于一个后端接口，但是却是直接呈现给Agent的内容

说得直白一点：**MCP从架构上是后端的一部分，但是从业务上来看其实属于前端，都是User Interface的范畴**

这也是为什么同样为后端接口，但是传统的HTTP接口往往优先考虑的是协议约定，你可以在里面塞各种抽象的业务字段和magic number；但对于MCP，格式一致性却没那么重要，更优先保证的往往是返回结构的可读性，能否准确、无歧义地传达出语义

## MCP与上下文交互范式的边界

从概念上来说，AI能接触到的资源往往是两类：静态的知识和动态的工具；但是从现象上来说，对于AI实际上是**万物皆上下文**的。而恰恰是因为这一点，许多人将MCP作为纯粹的工具调用，因为MCP要解决的上下文问题，本身就模糊了知识与工具的边界。

Claude Code和Skill其实带来了另一种让Agent与工作区交互的新范式：bash和脚本。关于这一个问题，我比较想先讨论另一个题外话

之前有人问过我一个问题：为什么最早的Agent框架是Python开发的，而最近比较流行的Agent框架是TypeScript开发的，如果自己想深入学习Agent相关的技术栈，为何还要深入研究Python相关的Agent框架。我的观点则是，这实际上恰好是Agent框架的两种主流形态和生态倾向：云端编排的Agent和本地编排的Agent

- 以Python为主要语言的Agent框架，主要解决的是运行在云端的Agent如何设计的问题，偏向基于网页端入口的服务端推理和模型编排
- 以TypeScript为主要语言的Agent框架，主要解决的运行在本地的Agent如何设计的问题，更加贴近ToC场景中更常用的桌面应用和本地工具链

为什么提到这一点，是因为你大概能注意到，以bash/脚本为途径的交互主要是伴随着本地Agent框架（如Claude Code、Open Code），以及随之带来的Skill产生的，其实话说到这里，答案已经很明了了：bash/脚本是用于处理**本地工作区**的上下文交互范式；而MCP则是用于处理**远端工作区**，尤其是在一个Agent内**集成多个不同业务系统的远端工作区**的上下文交互范式，这也是高亮总所说的：CLI=函数调用;MCP=服务调用

当然比较尴尬的一点是，其实MCP本身也支持本地工作区的交互，也就是除了**SSE**和**Streamable HTTP**的第三种通信协议——**STDIO**，这一方面也是因为**协议和接口本身也具有学习成本**，而Skill本身已经做成了可迁移的形态，相比之下，bash/脚本则显得要更加轻量化和敏捷

## 结论：MCP的定位到底是什么

话说回来，我在最前面已经说了，MCP的定位，是将原本割裂的Agent工作区和外部系统的工作区融合，建立起一个具有完整上下文关联关系的工作区。MCP的核心价值，就是当我们**同时存在多个业务系统，却只打算构建一个Agent系统**时，通过MCP的方式把外界系统的工作区和Agent系统的工作区打通，让Agent有能力同时操作多个业务系统的上下文

其实也只有这样子，我们才能实现**数字人**的概念，通过MCP的方式让Agent能够近似人类地操作一个系统（对于人类，操作接口是UI，即User Interface；对于Agent，操作接口是MCP），让Agent真正像一个员工一样在我们的系统上去操作业务的上下文。

MCP要解决的是面向业务场景的**上下文工程**的问题，这也回归到了MCP最开始的定义上，**模型上下文协议（Model Context Protocol）**。同时MCP也通过制定标准化协议，实现了**上下文工程的可迁移**。而完整的上下文工程，绝对不止是工具调用这么简单。
